Lab: Stillwater Co-op Bank

Category: Web Security / JWT

Vulnerability: JWT kid Path Traversal (privilege escalation)

Platform: webverse

Lab Description#

Briefing

Stillwater Co-op Bank has served its community since 1958 — four branches across two counties, twelve thousand members, share-draft accounts and small consumer loans only. The online portal was built one summer by the treasurer’s nephew and bolted onto the back-office wire-approvals queue a few years later when remote staff outgrew the paper log. The board’s compliance review last quarter flagged the whole stack as “long overdue for outside eyes.”

Create an Account#

We navigate to the registration page and open an account with a dummy name, email, and password.

Inspect the JWT#

After registration, the server redirects us to /dashboard. Intercepting this in Burp Suite, we can see a cookie named sw_token being sent. The Inspector panel on the right decodes it on the fly, and switching to the JSON Web Token tab gives us the full structure.

Header:

{
  "alg": "HS256",
  "kid": "2024-q4.pem",
  "typ": "JWT"
}

Payload:

{
  "role": "member",
  "member_no": "91000-8000",
  "iat": 1781420804,
  "exp": 1781449604
}

Two things stand out immediately:

  • The role claim drives access control — changing it to admin is the goal.
  • The kid header tells the server which key file to load when verifying the HMAC signature. If we control this value, we control which file on disk is used as the secret.

The Vulnerability — kid Path Traversal#

The kid (Key ID) parameter is supposed to be an opaque identifier that looks up a key in a safe store. When the server instead passes this value directly to a file-read call without sanitising it, an attacker can supply a path like ../../dev/null to redirect key lookup to any readable file on the system.

With HS256 in play — a symmetric algorithm — whoever knows the secret can produce a valid signature. By pointing kid at a file with empty or known content, we become the signer.

We have two exploitation paths.

Method 1 — kid → /dev/null (Null Byte Secret)#

Reading /dev/null on Linux always returns an empty byte sequence. This means the HMAC secret the server loads is empty — representable in Base64 as AA==. We craft a symmetric key with that exact value, sign a tampered token, and the server’s verification will match.

Step 1 — Create a symmetric key with a null byte secret

In Burp’s JWT Editor Keys tab, click New Symmetric Key → Generate, then manually replace the k value with AA==.

Step 2 — Modify the token

In the JSON Web Token tab of the intercepted request:

  • Set kid to ../../dev/null
  • Set role to admin

Step 3 — Sign

Click Sign, select the symmetric key we just created, choose Don't modify header, and hit OK. The response panel on the right immediately shows the Admin nav item — the forged token is already accepted.

Step 4 — Replace the cookie

Open Cookie Editor, find sw_token, paste in the forged JWT, and save.

Reload the page — the server loads /dev/null as the key, gets an empty byte, and verifies the HMAC we signed with that same empty byte. Admin access granted.

Method 2 — kid → /proc/sys/kernel/randomize_va_space (Known File Content)#

Sometimes a target hardens the null-byte path — the server may reject an empty secret or block /dev/null explicitly. In that case we need a file with known, predictable content.

/proc/sys/kernel/randomize_va_space is a Linux kernel tunable that stores the ASLR randomisation level. On virtually every default Linux system it contains a single character: 2 followed by a newline (\n).

Credit: Thanks to ShadowHound on the WebVerse Discord — signing with just 2 does not work. You must include the trailing newline, so the actual secret is 2\n.

Step 1 — Find the Base64 of 2\n

Open CyberChef, type 2 in the Input box, press Enter to add a blank line (the \n), and run To Base64. The output is Mgo=.

Step 2 — Create a symmetric key with Mgo=

In Burp’s JWT Editor Keys tab, click New Symmetric Key → Generate, then set k to Mgo=.

Step 3 — Modify and sign the token

  • Set kid to ../../proc/sys/kernel/randomize_va_space
  • Set role to admin
  • Click Sign, select the Mgo= key, choose Don't modify header, and hit OK.

Replace the cookie the same way as Method 1 — admin access granted.

Why This Works#

The server treats the kid header as a trusted file path, reads whatever file it points to, and uses that content as the HMAC secret. Since HS256 is symmetric, anyone who knows the secret can produce a signature the server will accept.

By redirecting kid to a file with empty or known content, we know the secret before the server even reads it. The forged token passes verification because we signed with the exact same bytes the server loads from disk.

A correct implementation should:

  • Treat kid as an opaque identifier looked up in a hardcoded allowlist — never as a filesystem path.
  • Sanitise or reject any kid containing path separators (/, ..) or null bytes.
  • Store signing secrets in a proper secrets manager, not as files reachable from the app’s read path.
  • Validate loaded key material meets minimum entropy requirements before using it.

Remediation#

IssueFix
kid passed directly to a file-read operationValidate kid against a strict allowlist; never treat it as a path
/dev/null usable as an HMAC secretReject empty or zero-entropy secrets at key-load time
Known-content kernel files usable as secretsEnforce minimum key entropy; reject single-byte secrets
role claim trusted from the JWT payloadAuthorise server-side against a database; never rely solely on token claims

The takeaway

The kid header is attacker-controlled input. Any server that feeds it directly into a readFile() call has handed the attacker a path traversal primitive — and with a symmetric algorithm like HS256, controlling the key file means controlling the signature. Two methods, one root cause: unsanitised kid.
